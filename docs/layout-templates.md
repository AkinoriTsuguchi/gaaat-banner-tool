# GAAAT バナー自動生成ツール開発メモ
### レイアウトテンプレート整理(過去バナー5パターン)

このメモは、GAAATの展示会バナーを「会期差し替え」「多言語対応」「作品の世界観に合わせたデザイン選択」まで自動生成できるツールを開発するための土台資料。

---

## 開発方針(前提)

- キャラクター原画・作品画像は **1pxも加工・変更しない**(固定レイヤーとして合成)
- 「世界観に合わせる」は完全な生成AIに背景を自由に作らせるのではなく、**下記5パターンのレイアウトテンプレートから自動選択**する方式で実現する(品質のブレ・監修コストを抑えるため)
- 配色(背景色・アクセントカラー・文字色)は作品画像から自動抽出する
- 会期情報・多言語テキストは差し替え可能な項目として設計する

## 世界観の自動選択ロジック(たたき台)

作品画像から抽出した配色・トーンをもとに、以下のようなルールでテンプレートを振り分ける想定。

- 暖色系・彩度高め・ポップ → テンプレート①
- モノトーン・和紙質感・墨系 → テンプレート②
- 特に指定なし・汎用 → テンプレート③(デフォルト)
- 暗色・単色スポット映え・重厚 → テンプレート④
- 寒色・グレー系・デジタル感 → テンプレート⑤

※最初はルールベースで始めて、運用しながら精度を調整するのが現実的。

## 次のステップ(Claude Codeでの実装範囲)

1. 上記5パターンをレイヤー構造のテンプレートファイル(SVGまたは画像合成用データ)として作成
2. キャラクター/作品画像を固定レイヤーとして合成する処理を実装(1px変更禁止)
3. 配色自動抽出ロジックを実装し、テンプレート自動選択ロジックと接続
4. 会期テキスト・多言語テキストの差し替え機能を追加(繁体字・簡体字・アラビア語(RTL)は専用フォント・レイアウト調整が必要)
5. GAAAT案件一覧マスタ(スプレッドシート)と連携し、会期×言語×都市の組み合わせを一括生成できるようにする

## 現状の実装メモ(2026-08-31 時点)

- [app.js](../app.js) / [index.html](../index.html) には、レイアウト選択プルダウンで切り替え可能な複数テンプレートが実装済み。
  - 「情報帯型(現行レイアウト)」: 元からあったカスタムレイアウト(テンプレート④相当ではなく独自構成)
  - テンプレート①キャラクター切り抜き型: `renderCutoutTemplate()`
  - テンプレート②縦書きタイトル型: `renderVerticalTitleTemplate()`
  - テンプレート③壁掛けフレーム型: `renderFrameTemplate()`
  - テンプレート④スポットライト額装型: `renderSpotlightFrameTemplate()`(RTL/アラビア語対応の参照実装。③④共通の額装描画は `drawPictureFrame()` に共通化)
  - テンプレート⑤サイバーUI型: `renderCyberUiTemplate()`
- 世界観の自動選択ロジックを実装済み: `classifyTemplateFromPalette()`。原画アップロード時に配色(背景の明るさ・彩度、アクセントの色相と生の彩度)からテンプレートを自動判定し、プルダウンに反映する。UIの「原画の配色からレイアウトを自動選択」チェックボックス(デフォルトON)でON/OFF可能。手動でプルダウンを変更すると自動でOFFになる。
- 実装済み機能: 案件マスタのスプレッドシート貼り付けパース、言語別テキストドラフト管理、原画からの配色自動抽出(背景色・アクセント・文字色コントラスト判定)、1080×1080キャンバスへの描画、PNGダウンロード、**都市×言語の一括生成(ZIP一括ダウンロード)**。

### 一括生成機能(2026-08-31 追加)

- 案件マスタを貼り付けると、複数都市がある場合はチェックリストが表示される(デフォルト全選択)。「言語」欄に追加済みの全言語 × チェックした全都市の組み合わせで自動生成し、ZIPでダウンロードする(`runBatchGenerate()` in [app.js](../app.js))。
- 都市×言語ごとに、会場名・会期日程（都市側）とタイトル/メインコピー/サブコピー（言語側）だけを差し替え、レイアウト・原画・配色は固定のまま描画する。
- ZIP化には [JSZip](https://cdnjs.cloudflare.com/ajax/libs/jszip/3.10.1/jszip.min.js) をCDNから読み込んで使用(オフライン等でJSZipが読み込めない場合は、個別PNGを順次ダウンロードするフォールバックあり)。
- ファイル名は `{都市}_{言語コード}.png`(重複時は連番を付与)。

## バナー用途(集客用 / オンライン販売用)(2026-08-31 追加)

- 新しい「バナー用途」セレクト(`els.bannerPurposeSelect`, `state.bannerPurpose`: `'venue'` | `'sale'`)を追加。データモデルを増やしすぎないよう、既存の会場名・会期フィールドを**そのまま流用して意味を切り替える**設計にした。
  - `sale`選択時、会場名欄のラベルが「販売サイト名」、会期欄が「販売期間(任意)」、サブコピー欄が「CTA文言」に変わる(`applyBannerPurposeUI()`)。中身のフィールド・データ構造は変えていない。
  - 新規フィールドは「価格・オファー文言」(`els.priceField`)ひとつだけ追加。`sale`モードの時だけ表示され、非空なら各テンプレートの会場/会期ラインに追記される。
  - 会場・会期・価格をまとめる処理は `buildInfoLineParts()` に共通化し、③④⑤①の情報ラインで共有(②と現行レイアウトは独自レイアウトのため会場テキストに価格を連結する形で個別対応)。
  - ③④②のCTAピル/バッジ/帯は、ユーザーが本文を何も入力していない場合に限り `saleCtaFallback()`(「ONLINE STORE」)にフォールバックする。ユーザー入力があれば常にそちらが優先される。
- 集客用(デフォルト)では表示・挙動は追加前と完全に同一(回帰確認済み)。

## Googleドライブ連携(2026-08-31 実装、要セットアップ)

「キャラクター原画」欄の下に、Googleドライブのフォルダから直接画像を選んで読み込める機能を追加した(`app.js` の「Google Drive import」セクション、`index.html` の `.drive-section`)。

- Google Identity Services (GIS) のトークンフローでOAuthログインし、Drive API v3のREST APIを直接fetchで叩く実装(gapiクライアントライブラリ不要)。
- フォルダURL(`.../drive/folders/{id}` など)または生のフォルダIDを貼り付けると、フォルダ内の画像ファイル一覧をサムネイル付きグリッドで表示。クリックすると通常のファイルアップロードと全く同じ処理(配色自動抽出→レイアウト自動選択→描画)が走る。
- 案件マスタを貼り付け済みの場合、ファイル名にPJコードまたは開催都市名が含まれるファイルを「候補」バッジ付きでハイライトする(`matchesParsedSession()`)。これは正式なPJコード⇔ファイルの紐付けではなく、あくまで「それらしい名前のファイルを目立たせる」ヒューリスティック。

### スプレッドシートURLからの自動取得(2026-08-31 追加)

「案件マスタから貼り付け」欄に、コピペ範囲の代わりにスプレッドシートのURL(該当タブを開いた状態、`#gid=...`付き)を貼るだけで自動取得できるようにした。

- Driveと同じGoogleログイン(同じOAuthトークン)で、追加スコープ `spreadsheets.readonly` を使ってSheets API v4を直接fetchで叩く。
- URLから`spreadsheetId`と`gid`を抽出 → `spreadsheets.get`でgid→タブ名を解決 → `spreadsheets.values.get`でそのタブのセル値を取得 → 取得した2次元配列をTSV文字列に変換して、**手動貼り付けと全く同じパーサー**(`applyParsedMasterText()`)に渡す、という流れ。パース・反映ロジックは完全に共通化されているので、手動貼り付けと自動取得で結果がズレることはない。
- 未ログインでURL取得ボタンを押すと案内メッセージを出す。ログイン後は「キャラクター原画」欄のGoogleログインと共有される。

### ⚠️ 動作させるには初期セットアップが必要(ユーザー側の作業)

Claude Codeからはユーザー自身のGoogle Cloudアカウントを操作できないため、OAuthクライアントIDの発行だけはGAAAT側で行う必要がある。手順:

1. [Google Cloud Console](https://console.cloud.google.com/) で新規プロジェクトを作成(または既存のものを利用)。
2. 「APIとサービス」→「ライブラリ」から **Google Drive API** と **Google Sheets API** の両方を有効化(案件マスタの自動取得にはSheets APIも必要)。
3. 「APIとサービス」→「OAuth同意画面」を設定(社内利用なら「内部」、外部共有もするなら「外部」を選択してテストユーザーを追加)。
4. 「APIとサービス」→「認証情報」→「認証情報を作成」→「OAuthクライアントID」→ アプリケーションの種類は **ウェブ アプリケーション** を選択。
5. 「承認済みのJavaScript生成元」に、このツールを開くURLのオリジンを追加(例: ローカルで動かすなら `http://localhost:8934`、社内サーバーにホストするならそのドメイン)。
6. 発行された **クライアントID**(`xxxxx.apps.googleusercontent.com` の形式)をコピーし、[app.js](../app.js) 内の

   ```js
   const GOOGLE_CLIENT_ID = 'YOUR_GOOGLE_OAUTH_CLIENT_ID.apps.googleusercontent.com';
   ```

   の値を置き換える。

設定が済むまでは「Googleでログイン」ボタンは無効化され、上に設定手順の案内文が表示される(未設定でもツール全体が壊れることはない)。設定後は、フォルダを読み込む前提としてそのフォルダがログインするGoogleアカウントと共有されている必要がある。

## レイアウト微調整パネル(2026-08-31 実装)

**背景**: 監修(版元)からのフィードバックには、①テキスト・日付・会場・配色などツールの入力項目で直せるものと、②要素の位置・サイズ・余白などレイアウト自体の調整の2種類がある。①は既存の入力欄を直して一括生成すれば済むが、②はこれまでテンプレートのコード自体を書き換えるしかなく、しかも「版元ごとに指摘箇所が違う」ため、ある案件向けにテンプレートを直すと別の案件に悪影響が出る恐れがあった。かといってPSDで都市×言語ぶん手直しするのは非常に手間、というのが元々の相談。

**対応**: テンプレートのコードは一切変えず、**その案件のセッション内だけで効く上書きレイヤー**として`state.adjustments`を追加した。

- 対象は版元指摘で特に多いという3カテゴリ×6項目: ロゴ・コピーライト・タイトル・メインコピー・サブコピー・原画(トリミング/位置)。各項目に「サイズ%(100=元のまま)」「横位置dx(px)」「縦位置dy(px)」の3つの数値入力(新設の「レイアウト微調整」フィールドセット、18個のnumber input)。
- `adj(key)`という安全アクセサ経由で、6テンプレート全ての該当描画箇所(ロゴ5箇所・コピーライト6箇所・タイトル6箇所・メインコピー5箇所・サブコピー5箇所・原画5箇所、計32箇所)に適用。フォントサイズには`* scale/100`を、描画座標には`+ dx`/`+ dy`を掛け合わせる形で、既存のレイアウト計算にオーバーレイする。
- **原画のトリミング/位置**は少し特殊で、`computeCoverRect()`/`drawCoverImageTo()`/`drawCoverImage()`に`zoom`(scale/100を渡す)と`panX`/`panY`(dx/dyをそのまま渡す)を追加。`zoom>1`で原画を中心から拡大トリミング、`panX`/`panY`で同じ枠内で見せる範囲を平行移動(実際に1px単位でズレないことをピクセル差分で検証済み)。①(キャラクター切り抜き型)の回転した原画パネルだけは`translate`前にdx/dyを加算する形で位置調整し、`drawCoverImageTo`にはzoomだけを渡している。
- `state.adjustments`はプロジェクト(セッション)単位で共有され、言語やあ都市を切り替えても保持される。`runBatchGenerate()`は一切この値に触れないため、一括生成の全都市×全言語に自動的に同じ調整が反映される。ページ再読み込みで消える点は他の入力項目と同じ(意図的、案件ごとの一時的な上書きという性質のため永続化していない)。
- 「この案件の調整をリセット」ボタンで全項目を一括で初期値(100/0/0)に戻せる。
- タイトルなど自動フィット(`fitFontSizeTruncate`)後のサイズにscaleを掛ける箇所は、scaleを100%超に上げすぎると再びはみ出す可能性がある(自動サイズ調整とは違い、目視確認しながら手動で追い込む前提の機能として許容)。

**今後の拡張候補**(ユーザーへの確認済み: 将来的にはドラッグ操作も欲しいとのこと): 上記の数値入力に続き、キャンバス上でのドラッグ/ホイール操作は下記「レイアウト微調整のキャンバス直接操作」で対応済み。

## レイアウト微調整のキャンバス直接操作(2026-08-31 実装)

**背景**: 上記の数値入力パネルを実装した際、「まずは数値入力から。将来的にキャンバス上でドラッグできるようにする拡張余地は残してある」という前提で設計していた。その直後にユーザーから「対応して」と明示的な依頼があり、同日中にドラッグ/ホイール操作を実装した。

**対応**: 数値入力(`state.adjustments`)とキャンバス操作を同じ状態に対して行う、双方向連動の仕組みとして実装。

- 6テンプレートそれぞれの調整可能要素(ロゴ・コピーライト・タイトル・メインコピー・サブコピー・原画、計36箇所)の描画直後に`recordBounds(key, x, y, w, h)`を呼び、「その要素が実際にネイティブ1080px座標のどこに描かれたか」を`state.elementBounds`に記録する。`render()`の先頭で毎回リセットしてから各テンプレート関数を呼ぶので、言語・文字数・現在のadjustments値によって位置やサイズが変わっても常に実際の描画結果と一致する。
- キャンバスの`mousemove`でその点をヒットテスト(`hitTest()`、後から描画された=画面上で手前の要素を優先)し、該当要素があればカーソルを`move`にし、青い破線のハイライト枠(`#adjustHighlight`)とラベルを表示。
- `mousedown`でその要素を掴み、`mousemove`中は移動量をそのまま`state.adjustments[key].dx/dy`に加算して`render()`を呼び直す(ハイライト枠は黄色に変化)。`mouseup`で確定。ドラッグ量はキャンバスの表示サイズ(CSS px)とネイティブ1080px座標のスケール差を`getBoundingClientRect()`で補正して計算しているため、ブラウザの表示倍率に関わらず1:1でずれなく動く。
- 要素の上でホイール操作すると`state.adjustments[key].scale`が4%刻みで増減する(上スクロール=拡大、下スクロール=縮小、10〜400%にクランプ)。
- ドラッグ/ホイールで変わった値は、対応する数値入力(`adjLogoDx`など)にも`syncAdjustmentInputs()`でその場で反映されるため、「キャンバスでだいたいの位置を決めてから数値入力で微調整する」という使い方もできる。逆方向(数値入力→キャンバス)は既存の`render()`呼び出しでそのまま反映される。
- 回転を伴う要素(①キャラクター切り抜き型の斜め原画パネル、②縦書きタイトル型の回転タイトル文字列)は、当たり判定・ハイライト枠を「軸に平行な矩形での近似」にしている(回転後の正確な四角形ではない)。ドラッグの移動量自体は常に非回転の親座標系(dx/dyがそのまま効く座標系)で計算されるため、この近似は当たり判定・見た目のハイライト枠のズレに留まり、実際のドラッグ操作の精度には影響しない(実機で±1px程度の誤差でdx/dyが反映されることを確認済み)。
- ⑤サイバーUI型のサブコピー(CTAバッジ)は、この実装以前は数値入力パネルの対象カテゴリに含まれていながら実際には描画コードにdx/dy/scaleが結線されておらず、ドラッグしても見た目が動かない状態だった(数値入力パネル実装時に「マイナー、スキップ」と記録されていた既知の抜け)。ドラッグ機能を通す過程でこの結線漏れも合わせて修正した。

**動作確認**: `canvas`に`clientX/clientY`付きの`MouseEvent('mousemove')`を直接dispatchしてハイライト表示・ホバー判定を確認した上で、ブラウザ操作ツールでの実際のドラッグ(ロゴのdx/dy、①の回転原画パネルのdx/dy、②の回転タイトルのdx/dy)とホイール操作(ロゴのscale)がいずれも狙った量だけ`state.adjustments`に反映されることを確認済み。6テンプレート全てで`render()`がエラーなく完走し、全調整可能要素の`recordBounds`が正しいキーで登録されることも確認済み。

## レイアウト微調整のUndo/Redo(2026-08-31 実装)

**背景**: ドラッグ操作の実装直後、ユーザーから「これから着手してほしい」機能として明示的に要望があった。ドラッグで意図せず要素を動かしてしまっても戻せないのはストレスになる、という運用上の懸念に対応。

**対応**: `state.adjustments`オブジェクト全体をスナップショットする方式のUndo/Redoスタック(`undoStack`/`redoStack`)を追加。個別フィールドの差分ではなく丸ごとクローンする方式にしたのは、6カテゴリ×3項目程度なら複製コストが無視できるのと、「リセット」のように複数カテゴリを同時に変える操作でも1回のUndoで確実に元へ戻せるため。

- ドラッグ中の連続する`mousemove`、ホイールの連続ティック、数値入力欄への1文字ごとの`input`イベントなど、細かい変更が大量に発生する操作は、「ユーザーの体感としての1アクション」ごとに1つのUndoステップへまとめる(コアレシング)。`recordAdjustmentChange()`を変更のたびに呼ぶが、実際にスナップショットを取るのは連続した変更列の最初の1回だけで、以降は500ms(`UNDO_COALESCE_MS`)のデバウンスタイマーをリセットし続ける。
- 「ドラッグのmouseup」「リセットボタン」のように操作の終わりが明確なものは、そのタイミングで`commitAdjustmentUndoGroup()`を呼んで即座にグループを確定する(デバウンスタイマーの満了を待たない)。ホイールや数値入力のように終わりが明確でない操作は、タイマー満了(操作が止まって500ms経過)で自動確定する。
- Undoボタン・Redoボタン(数値パネル内、リセットボタンの隣)に加えて、`Ctrl+Z`(Windows)/`Cmd+Z`(Mac)でUndo、`Ctrl+Shift+Z`または`Ctrl+Y`でRedoに対応。ただしタイトル・会場名・キャッチコピーなどのテキスト入力欄にフォーカスがある間は、ブラウザ標準のテキストUndoを妨げないようこのショートカットを無効化している(`isTextEditingContext()`で判定)。
- Undo/Redoで戻した値は、対応する数値入力欄(`adjLogoDx`など)にも`syncAdjustmentInputs()`で即座に反映される。新しい変更が発生すると(次のドラッグ・入力など)、Redo履歴は破棄される(一般的なUndo/Redoの挙動と同様)。
- スタックの上限は100件(`UNDO_MAX`)。長時間の作業でも際限なく履歴が積み上がらないようにする安全弁で、実運用でこの上限に達することは想定していない。

**動作確認**: 数値入力→Undo→Redo、5回分の`mousemove`イベントを束ねた擬似ドラッグ(1回のUndoステップにまとまることを確認)→Undo、リセットボタン→Undo(リセット前の値に戻ることを確認)、テキスト欄にフォーカスした状態での`Ctrl+Z`が`state.adjustments`に一切影響しないことを、それぞれ`state.adjustments`と`undoStack`/`redoStack`の中身を直接読み取って確認済み。

## 自動翻訳(2026-08-31 実装、セットアップ不要)

前段の「未翻訳フィールドの警告」だけでは、警告ダイアログを読まずに素通りされて全言語が未翻訳のまま書き出される事象が実際に再発した。ユーザーへの確認の結果、手入力方式から自動翻訳方式に転換することになった。当初はGoogle Cloud Translation APIで実装したが、有効化に請求先アカウント(課金)登録が必須と分かり、「課金なしで自動翻訳したい」という要望を受けて **MyMemory**(https://mymemory.translated.net/doc/spec.php)ベースに切り替えた。

- MyMemoryはサインアップ・APIキー・課金設定が一切不要の無料翻訳API。`fetch`でGETするだけ(CORS対応済み、SDK不要)。無料枠は匿名利用で1日あたり単語数5,000語程度(このツールの用途では通常十分)。
- 「言語」欄に、`scanTranslationGaps()`が未翻訳と判定した項目がある間だけ「未翻訳の項目を自動翻訳」ボタンが表示される。押すと、各言語グループ内で日本語があれば日本語を、なければ設定順で最初の言語を「原文」とみなし、そこから他の言語へ機械翻訳して各言語のドラフトに書き込む(`autoTranslateUntranslated()`)。
- MyMemoryの無料エンドポイントは1リクエスト1文字列のみ(バッチ非対応)なので、タイトルなど複数行のフィールドは改行で分割し、行ごとに順番にAPIを呼び出して(`translateLines()`)結果を元の行位置に戻す。リクエスト間に150msの間隔を空け、無料の共用サービスへの配慮としている。
- 中国語だけは`zh-Hans`/`zh-Hant`という内部コードを`zh-CN`/`zh-TW`に変換する必要があり、`translateLangCode()`で対応。
- 機械翻訳なので、翻訳後も内容の確認・手直しは人間が行う前提(完了メッセージにもその旨を明記)。翻訳後は該当言語チップの「！」バッジが自動的に消える。
- **品質の実例(動作確認時)**: 「歴代シリーズを横断する 唯一無二の展示・販売会。」→ "A one-of-a-kind exhibition and sales event across successive series."(自然)。一方で固有名詞「パトレイバー」が音訳で"Patraber"と誤訳される(正しくは"Patlabor")など、造語・固有名詞の誤訳は起こりうる。無料の翻訳エンジンである以上の限界として認識し、「内容を必ず確認してください」の文言をそのまま残している。

セットアップ手順は不要で、初回から動作する。将来的により高品質な有償エンジン(Google Cloud Translation、DeepLなど)に切り替えたくなった場合は、`translateLine()`関数内のfetch呼び出しを差し替えるだけで済むよう、翻訳ロジックはこの1関数に閉じ込めてある。

## レイヤー分け出力(2026-08-31 実装)

「レイヤー分け出力」フィールドセットから、背景・原画・装飾・テキストの4レイヤーに分けて書き出せる。

- **ZIP(レイヤー別PNG)**: 各レイヤーを透過PNGとして、フラット化した完成形と合わせてZIPに(`downloadLayersZip()`)。
- **PSD**: [ag-psd](https://github.com/Agamnentzar/ag-psd)をCDNから遅延読み込みし(初回クリック時のみ、約800KB)、4レイヤーの名前付きPSDとして書き出す(`downloadPsd()`)。Photoshopで開くと、背景・原画・装飾・テキストの各レイヤーを個別に表示/非表示・移動できる。

### 実装方式(技術メモ)

6テンプレートの描画コード(約2500行)を一切書き換えずにレイヤー分離を実現するため、`ctx` をProxyにして「今どのレイヤー用オフスクリーンcanvasに描画するか」を実行時に切り替える方式にした([app.js](../app.js) 冒頭の「Layer system」セクション)。

- 各テンプレート関数の中に、既存の `// ---- ◯◯ ----` という区切りコメントの直後に `useLayer('text')` のような1行を挿し込むだけで、その区切り以降の描画がその名前のレイヤー(オフスクリーンcanvas)に向かうようになる。個々の `fillRect`/`fillText`/`drawImage` 呼び出し自体は一切変更していない。
- `render()` は `createLayers()` (4枚のレイヤーcanvasを新規作成) → 各テンプレート関数 → `compositeLayers()` (背景→原画→装飾→テキストの順で実キャンバスに合成)という流れ。通常のプレビュー表示・PNGダウンロード・一括生成(ZIP)は今まで通りこの合成済みキャンバスを見ているだけなので、影響を受けない。
- **ハマったポイント**: `drawPictureFrame()`(③④共通の額装描画)は、額縁→フィレット→マット→原画、という順に「手前の色で奥の色を塗りつぶす」ことで額装を表現していた。これは単一キャンバスなら正しく動くが、マット(装飾レイヤー)と原画(原画レイヤー)を別キャンバスに分離し、装飾レイヤーを原画レイヤーより上に合成する今の方式では、マットの塗りつぶしが原画を覆い隠してしまう。額縁・フィレット・マットを「原画窓の形に穴を開けたリング」として`evenodd`クリップで塗ることで解決した(ドロップシャドウも同様にリング状に塗って対応)。
- レイヤー分類は9種(2026-08-31 追記: 当初は`text`1本だったが、「テキスト項目」パネルの入力欄ごとに分けたいという要望を受けて分割): `background` / `artwork` / `decoration` / `title`(展示会タイトル) / `dates`(会期情報) / `venue`(開催会場名・価格/オファー文言) / `mainCopy`(メインコピー) / `subCopy`(サブコピー) / `copyright`(コピーライト)。
  - 会場名・会期・価格を1行にまとめて表示している箇所(③④⑤①のinfoライン)は、`drawInfoLine()`で各パートを個別に測定・配置しつつ、パートごとに別レイヤーへ描画するようにした(区切り文字だけは`decoration`)。
  - CTAテキストのようにサブコピー/メインコピーいずれかにフォールバックする箇所は、実際に使われた側のフィールドのレイヤーに描く(両方空ならデフォルトで`subCopy`)。
- PSD書き出しの正しさは、書き出した直後に ag-psd 自身の `readPsd()` で読み戻し、レイヤーを合成した結果と実キャンバスをピクセル比較して検証済み(差分ゼロ)。

### 直った不具合(2026-08-31)

- `LOGO_DATA_URL`(GAAATロゴのbase64埋め込み)が壊れており、全テンプレートでロゴが無言で表示されていなかった。[logo_horizontal_cropped.png](../logo_horizontal_cropped.png) から正しくbase64を再生成して修正。今後ロゴ画像を差し替える場合は、このファイルをbase64化して `LOGO_DATA_URL` を置き換えること。

### Meta広告配信を前提としたテキストサイズの引き上げ(2026-08-31)

Meta(Instagram/Facebook)のフィード広告として配信する前提で、実際のフィード上での表示サイズ(1080px原寸ではなく、スマホでは数百px幅まで縮小される)を考慮し、6テンプレート全ての「主見出し以外」の文字サイズを軒並み引き上げた。

- **副産物のバグ修正**: サイズ引き上げの過程で、`drawInfoLine()`(会場名・会期・価格などを1行に結合して描画する共通関数)に幅の上限が一切なく、フォントを大きくしたら①テンプレートの会期情報が原画にはみ出す実際の不具合が発生した。`drawInfoLine()`に`maxWidth`引数を追加し、指定幅を超える場合は自動でフォントを縮小(最大70%まで)するようにして修正。他3テンプレートの同種の呼び出し箇所にも同じ上限を追加済み。

### ⑤サイバーUI型のタイトルを全面的に強化(2026-08-31)

ユーザーから「このテンプレも(展示会)タイトルが小さすぎる」と直接指摘があった。実際、⑤だけは展示会タイトルが18pxの等幅フォント1行タグ(`[ EXHIBITION ] タイトル`)のみで表現されており、フィード広告として縮小表示されるとほぼ判読不能だった(他5テンプレートは前段の対応で見出しをきちんと拡大済みだったが、⑤は「タイトル＝小さなHUDタグ」という意図的なデザインのままだったため取り残されていた)。

- `[ EXHIBITION ]` という小さなキッカーラベル(等幅フォント、HUD感を維持)はそのまま残しつつ、その下に他テンプレート同様のサイズ感(最大58px)で展示会タイトル本文を独立した見出しとして追加。

### `fitFontSize`が「実際にはみ出さない」ことを保証していなかった問題(2026-08-31、複数箇所で実際に発生)

ユーザーが自動翻訳で実際にイタリア語のバナーを複数生成し、「全体的に修正が必要かも」とスクリーンショットを共有してくれたことで発覚。

**根本原因**: `fitFontSize()`はフォントサイズを`minSize`まで縮小して、そこで諦めて返すだけの実装で、縮小してもまだ収まらない場合にテキストが実際に指定幅を超えて描画されることを一切防いでいなかった。日本語の短いラベルでは問題にならなかったが、翻訳後の文字列(特にイタリア語などは日本語の2〜3倍の文字数になりがち)だと、最小サイズまで縮めても1行に収まらないケースが現実に発生する。

**実際に発生した不具合(3箇所)**:
1. ③壁掛けフレーム型: 下段の「作品名(左)＋CTAピル(右)」のうち、作品名が長いタイトルで右側のCTAピルに完全に重なり、両方とも判読不能なテキストの塊になった。
2. 情報帯型(現行レイアウト): 開催会場名が左カラムの幅を超え、右側の原画にはみ出して重なった。
3. ②縦書きタイトル型: 縦書きタイトル(横書きフォールバック)が想定より大きくレンダリングされ、下部のCTA帯を突き抜けてキャンバス下端まで到達した。この3つ目の原因は少し特殊で、`fitFontSize`自体は正しく直したはずが実際には直っておらず、原因は別にあった(次項参照)。

**対応**:
- `fitFontSizeTruncate()`という新しいラッパー関数を追加。`fitFontSize()`で縮小してもまだ指定幅を超える場合、末尾を「…」で省略して確実に幅内に収める。戻り値は`{size, text}`で、描画には必ず`.text`(切り詰め後の文字列)を使う。
- ①③④情報帯型・②縦書きタイトル型の、原画や別要素と衝突しうる全ての単一行タイトル/CTA/会場名の`fitFontSize`呼び出しを`fitFontSizeTruncate`に置き換え(合計8箇所)。
- ③壁掛けフレーム型の「作品名」ラベルは、そもそも上部の大見出しと完全に同じ内容を繰り返しているだけの冗長な要素だったため、パッチで延命せず削除。CTAピルが行全体の幅を使えるようにし、ピル自体も`fitFontSizeTruncate`で幅を保証。

**②のテンプレートだけ直らなかった理由(测定方法の不一致)**: `fitFontSizeTruncate`を適用したにもかかわらず②の横書きフォールバックだけ症状が再現し続けた。原因は、文字間隔(letter-spacing)付きで描画する`drawSpacedText()`が「1文字ずつ`measureText`して幅を積算する」方式なのに対し、`fitFontSize`/`fitFontSizeTruncate`は「文字列全体を1回`measureText`する」方式で幅を見積もっており、この2つの測定方法の結果が(特にOswaldのようなコンデンス書体で)大きく乖離していたこと。文字列全体としての測定は文字ごとの測定の合計よりかなり小さく出ることがあり、fitFontSize側は「収まっている」と判定したのに、実際に`drawSpacedText`で描画すると大幅にはみ出す、という食い違いが発生していた。`measureRunWidth()`という共通の幅測定関数を追加し、`drawSpacedText`と全く同じ「1文字ずつ積算」方式に統一。`fitFontSize`/`fitFontSizeTruncate`はこの関数経由でのみ幅を測るように変更し、以後は測定方法の不一致が起きないようにした。
- 3箇所とも、実際に長いイタリア語文字列(`state.currentLang`をその言語に正しく設定した状態)でレンダリングし直し、はみ出し・重なりが解消したことを画像で確認。

## 未翻訳フィールドの警告(2026-08-31 実装)

**報告された不具合**: 英語を含む複数言語で書き出したところ、展示会タイトル・メインコピーが日本語のまま出力された(会期情報の日付表記は正しく英語形式になっていた)。

**原因**: 展示会タイトル/メインコピー/サブコピーは「言語別」がデフォルトONの per-language フィールドで、新しい言語タブを初めて開いた瞬間に(`loadDraft()`内で)現在の言語のテキストがそのまま「訳す前の下書き」としてコピーされる仕様。ここで実際に訳文へ書き換えないまま一括生成やダウンロードを行うと、コピーされた原文がそのまま出力される — かつエラーも警告も一切出ない。ユーザーが英語タブを開いただけで「翻訳した」と思い込みやすい、静かな罠だった。

**対応(1回目)**: `findUntranslatedFields()`を追加し、設定済みの全言語を横断して、タイトル/メインコピー/サブコピー(コピーライトは意図的に除外— 複数言語で同一表記のままにしたいケースが多いため)のテキストが2言語以上で完全一致していないかチェックする。1件でも見つかれば、実際の書き出し操作(PNGダウンロード・一括生成・レイヤーZIP・PSD)の直前に`confirm()`で警告し、キャンセルすれば書き出しを中止できる。

**再発**: 上記の`confirm()`は書き出し直前の一度きり・ダイアログを閉じれば消える性質上、読まずに閉じられて素通りしてしまい、6言語すべて未翻訳のまま書き出される事象が実際に再発した。

**対応(2回目、恒久対策)**: 書き出し時の一度きりの警告に加えて、`scanTranslationGaps()`(旧`findUntranslatedFields`のコア判定を切り出したもの)を使い、「言語」欄の各言語チップに、まだ未翻訳の可能性がある言語には常時「！」バッジを表示するようにした(`renderLangBar()`を拡張)。バッジはタイトル/メインコピー/サブコピーの入力中もリアルタイムに更新される(該当3フィールドに`input`リスナーを追加し`renderLangBar()`を都度呼び出す)。あわせて言語欄の下に「未翻訳の可能性: 展示会タイトル（日本語・Englishが同じ内容）」のように具体的な項目名を列挙するヒント文も常時表示するようにし、編集中ずっと目に入る形にした。書き出し時の`confirm()`警告はそのまま残しているので、二重の安全網になっている。

`javascript_exec`で「言語を追加しただけで未編集→全チップに！バッジ+ヒント文が出る」「1言語ぶん翻訳→そのチップだけバッジが消える」の両方をライブ更新込みで確認済み。

## 要素の非表示・会期情報の編集・調整範囲の拡大・タイトル欄の見直し(2026-09-01 実装)

ドラッグ機能・Undo/Redoの実装直後、ユーザーから4件まとめて要望があった。①要素の削除（例: サブコピーを丸ごと消したい）、②会期情報も編集したい、③年（2026）を任意で消したい、④展示会タイトルの初期値がパトレイバー基準で特殊、⑤原画の移動範囲をもっと広げたい。着手前に、案件マスタ「案件一覧マスタ」スプレッドシート（`一覧`シート、企画タイトル列）を50件以上目視確認し、事実確認をしてから対応した。

### ①要素の非表示(削除)

**発覚した実際の不具合**: サブコピーを空欄にしても、③④②⑤（フレーム型/スポットライト型/縦書き型/サイバーUI型）では`saleCtaFallback()`等の代替文言（例:「ONLINE STORE」）が自動的に入ってしまい、実際には消せなかった（情報帯型・①切り抜き型は元々空欄で非表示になる作りだった）。テンプレートによって挙動がバラバラだったのを、明示的な「非表示」フラグで統一。

**対応**: `state.adjustments`の各カテゴリに`hidden`フラグを追加し、レイアウト微調整パネルに「非表示」列（チェックボックス）を追加。

- ロゴ以外（コピーライト・タイトル・メインコピー・サブコピー・会期情報・原画）は`LAYER_ORDER`ですでに1項目1レイヤーに分かれている(`compositeLayers()`が`LAYER_ORDER`を順にflattenしている)仕組みを利用し、「非表示」はそのレイヤーのcompositeだけをスキップする方式にした。描画自体（`recordBounds`含む）は普段通り実行されるので、(a) レイヤー分けZIP/PSD書き出しには影響しない（Photoshop側で普通に復活できる）、(b) 非表示中でもキャンバス上でドラッグして位置を仕込んでおける、という2つの副次的なメリットがある。
- ロゴだけは`decoration`レイヤーを常時表示の帯・スクリム・HUD枠と共有しているため、上記のレイヤーcompositeスキップ方式が使えず、5箇所の描画呼び出し自体を`if (!logoAdj.hidden) { ...drawImage... }`で個別に囲む方式にした。
- 「この案件の調整をリセット」は`hidden`も含めて全項目を初期値に戻す。Undo/Redoは既存の`state.adjustments`丸ごとスナップショット方式にそのまま乗るので追加対応不要だった。

**動作確認**: オンライン販売モードでメインコピー・サブコピーを両方空にした状態（＝フォールバック文言「ONLINE STORE」が出るはずの状態）で③のサブコピー枠を非表示にし、該当領域のピクセル合計値が非表示前後で変化することを確認（フォールバック文言が実際に消えていることの確認）。

### ②③会期情報の編集(自由入力)・年の表示切り替え

**対応**: 「会期情報」を7つ目の調整対象カテゴリとして追加（位置・サイズ・非表示すべて対応）。加えて、テキスト項目に以下2つを新設。

- 「会期情報の表示テキスト（任意・自由入力）」— 空欄なら従来通り開始日・終了日から自動生成、何か入力されていればその文字列がそのまま会期情報として使われる（通期開催や「随時」など、開始日・終了日のペアでは表現できないケースに対応）。自由入力時は、情報帯型の年ラベル・区切り線（開始日と終了日をつなぐ斜め線）は意味を失うため自動的に非表示になる。
- 「年（例: 2026）を表示する」チェックボックス — 情報帯型でのみ意味を持つ（他5テンプレートはもともと年を表示していない）。オフにすると年の行が消え、その分レイアウトが詰まる。

**位置・サイズ調整の実装範囲**: ②（縦書きタイトル型）と情報帯型は日付ブロックが単独で描画されているため、独立して位置・サイズを動かせる。③④①⑤（フレーム型/スポットライト型/切り抜き型/サイバーUI型）は`buildInfoLineParts()`+`drawInfoLine()`で会場名・会期・価格を1本の行にまとめて描画する設計のため、「会期情報」の位置調整はその行全体（会場名・価格も含む）を動かす形になる。会期だけを独立して動かすには行の分割描画が必要で、実装コストに対して効果が薄いと判断し、この4テンプレートでは「行全体が一緒に動く」仕様であることをパネルのヒント文で明記した。

**動作確認**: 自由入力テキストへの切り替えで日付ブロックの高さ・幅が想定通り変わること（情報帯型: 年表示ON時153.6px→年OFF時110.4px→自由入力時58pxの1行）、サイバーUI型で位置・サイズ調整（scale 150% / dx 40 / dy -20）が反映されること、非表示化で該当領域のピクセル合計が変化することを確認済み。

### ⑤原画（および全カテゴリ共通）の調整範囲の拡大

**実際の制約**: ドラッグ中の`mousemove`リスナーが`canvas`要素にしかバインドされておらず、カーソルがキャンバスの表示領域（1080pxのネイティブ座標に対し画面上は数百px程度に縮小表示）の外に出た瞬間、それ以上ドラッグが追従しなくなり「途中で動かなくなる」状態だった。数値入力欄には元々上限がなかったため、範囲が実質的に狭かったのはドラッグ操作だけだった。

**対応**: ドラッグ追従用の`mousemove`リスナーを`canvas`から`window`に変更（ホバー表示用の`mousemove`は従来通り`canvas`のまま分離）。あわせてホイールでのサイズ調整のクランプ範囲を10〜400%から5〜1000%に拡大。

**動作確認**: `mousedown`後にキャンバス表示領域の外（-2000px相当）まで`window`に対して`mousemove`をdispatchし、dx/dyがクランプされず正しくスケール換算された値まで追従することを確認。ホイール200回転相当のイベントでscaleが900%まで、さらに追加で1000%の上限にクランプされることを確認済み。

### ④展示会タイトルの初期値をパトレイバー基準から標準的な長さへ変更

**確認内容**: ユーザー指示に基づき、案件マスタ「案件一覧マスタ」（`https://docs.google.com/spreadsheets/d/1pjSfRYR17r1onw8RU3f-M1RsIDBpUUljqnV0zjgt-XU/`）の`一覧`シート、企画タイトル列を50件以上目視確認。実際の企画タイトルはほぼ全て1行の短い文言（例:「頭文字D ART EXHIBITION by GAAAT」「石ノ森章太郎『サイボーグ009』展」「キャプテン翼 ONE WORLD ONE TEAM ART EXHIBITION」）で、複数行にまたがる特殊な構成（大見出し／英字タグライン／正式名称の3段）を使うケースはパトレイバー展（デザイン参照元バナーの元ネタ）くらいしか見当たらなかった。

**対応**: タイトル欄の初期値を、3行構成のパトレイバー実例（"PATLABOR" / "THE MOBILE POLICE" / "Mobile Police Patlabor - Art of GEN【RELOAD】"）から、単一行の一般的な例（"GINTAMA ART EXHIBITION by GAAAT"）に差し替え。ラベルとヒント文も「通常は1行でOK。2行目・3行目は必要な案件だけの任意欄」という位置づけが伝わるように書き換えた（2行目＝英字タグライン／3行目以降＝正式名称という機能自体は残している。パトレイバーのような特殊案件では引き続き使える）。

### 上記の実装直後に発見・修正した不具合(2026-09-01、ユーザー指摘+全体レビュー)

ユーザーから「この巨大なスラッシュが気になる」との指摘を受け、それをきっかけに全テンプレート・新機能の組み合わせを一通り再検証し、他にも実際にレンダリングが壊れる不具合を複数発見・修正した。

1. **情報帯型の日付スラッシュ接続線が異常に大きい**: 開始日・終了日の2行の間を結ぶ斜め線が、2行分の高さ（約100px）をそのままカバーする形で描かれており、隣接する58pxの日付テキストに対して明らかに太すぎ・長すぎだった。2行の中間点を中心に、日付テキストのキャップハイトに近いサイズ（フォントサイズの0.84倍）へ縮小。
2. **原画を非表示にすると②⑤（縦書きタイトル型/サイバーUI型）で完全に透明な穴が開く**: この2テンプレートは全面原画のフルブリード構成で、原画の背後に単色の背景レイヤーが無かった（「原画未アップロード時」のプレースホルダー用の背景塗りが原画と同じ`artwork`レイヤーに同居していたため、非表示化するとその塗りごと消えていた）。`background`レイヤー（常に表示される）に単色背景を独立して敷くよう修正。
3. **会期情報の自由入力テキストに長さ制限が無く、情報帯型・②縦書きタイトル型でキャンバス外/原画上にはみ出す**: 実際に27〜30文字程度の自由入力（「2026年8月21日（金）〜9月30日（水）会期中無休・最終日は17時閉場」）を試したところ、情報帯型では原画の上に文字が乗り上げ、②では文字列がキャンバスの下端（1080px）を超えて画像の外まで続いていた。開始日・終了日から自動生成する日付表示は常に短い（「08.21 (Fri.)」程度）ため元々問題にならなかったが、自由入力はどんな長さもあり得るため、`fitFontSizeTruncate`で幅に収まらなければ縮小→省略（「…」）するガードを追加した。③④①⑤（`drawInfoLine`使用）は元々70%までの自動縮小を持っていたため、同じ文字列でも問題なかった（追加対応不要と確認）。
4. **②縦書きタイトル型のタイトルが長いと自力でキャンバス外に流れ出る**: 上記③のテスト中に偶然発覚。CJK（日本語/中国語）用の縦書きタイトルは文字ごとに積み上げる独自の縮小ロジックを持っていたが、フォントサイズの下限（32px）が32文字クラスの長いタイトル（今回のデフォルト値変更で採用した"GINTAMA ART EXHIBITION by GAAAT"が該当）に対して大きすぎ、下限まで縮小してもなお必要高さがキャンバス高さ(1080px)を超え、バナー下端からはみ出していた（実測: 985.8px分の高さ、開始位置102pxを足すと1087.8pxで1080pxを8px弱超過）。他の`fitFontSizeTruncate`利用箇所と同様、縮小だけでなく最終手段としての省略（「…」）を追加し、確実に収まるようにした。あわせて、縮小判定の計算式に実際の行送り係数(1.06倍)が抜けていた誤差も修正。

いずれも実際に該当条件でレンダリングし、要素の座標・高さがキャンバス範囲内に収まること、および画像として目視でも崩れていないことを確認済み。

## 一括生成前のサムネイル一覧プレビュー(2026-09-01 実装)

## 翻訳済みテキストの「原文変更後」検知(2026-09-01 実装)

**背景**: 既存の「未翻訳フィールドの警告」（`scanTranslationGaps()`）は、ある言語のテキストが他の言語と一字一句同じ（＝案件マスタからコピーされた下書きのまま、まだ訳文に書き換えられていない）場合だけを検知する仕組みだった。しかし、一度翻訳した後に日本語の原文だけを後から修正するケースは検知できなかった——翻訳済みの英語などは原文と一字一句異なる文章になっているため、「同じ内容かどうか」だけを見る既存のチェックでは引っかからない。ユーザーからこの「変更後」検知の実装依頼があった。

**対応**: `state.translationSnapshots`（`{ [言語]: { [フィールド名]: その訳文を書いた時点の原文テキスト } }`）を追加し、原文（日本語があれば日本語、無ければ最初に設定した言語＝`getSourceLang()`）の現在のテキストとスナップショットを比較する`scanStaleTranslations()`を新設した。

- スナップショットは2つのタイミングで記録される: ①自動翻訳（`autoTranslateUntranslated()`）が実際に翻訳した直後、②言語別フィールド（タイトル/メインコピー/サブコピー）を、原文の言語以外を表示中に手で編集した時（人力で訳文を書いた/直した、という確認の意味）。どちらの場合も「その時点の原文テキスト」をスナップショットとして保存する。
- `scanStaleTranslations()`は、スナップショットが記録されている言語・フィールドについてのみ、現在の原文テキストとスナップショットを比較する。スナップショットが無い（＝一度も翻訳・確認されたことが無い）場合は判定対象にしない——それは既存の`scanTranslationGaps()`（一字一句同じ＝未翻訳）が担当する領域であり、二重に警告を出さないようにするため。
- 検知結果は既存の「！」バッジ・翻訳警告ヒント文・書き出し前の確認ダイアログ（`confirmProceedWithUntranslated`）すべてに合流させた。「未翻訳」と「原文変更後」は文言を分けて表示する（例:「サブコピー（Englishが原文の変更前のまま）」）。
- 「未翻訳の項目を自動翻訳」ボタンは「未翻訳・要更新の項目を自動翻訳」に改称し、`scanTranslationGaps()`の未翻訳ジョブと`scanStaleTranslations()`の要更新ジョブを同じキューにまとめて処理するようにした。検知だけして直す手段が無いのでは片手落ちになるため、既存の自動翻訳の仕組みにそのまま乗せる形で「検知→ワンクリックで再翻訳」まで完結させた。

**動作確認**: 日本語→英語で自動翻訳（実際にMyMemory APIを呼び出し）→スナップショット記録を確認→日本語タイトルを編集→`scanStaleTranslations()`が英語タイトルを検知することを確認→再度自動翻訳して解消されることを確認。あわせて、自動翻訳を使わず英語欄を手で直接編集した場合もスナップショットが記録され、その後の日本語編集で正しく「要更新」判定されることを確認済み。書き出し前の確認ダイアログ用の`findUntranslatedFields()`にも反映されることを確認。

## 四隅ドラッグでのリサイズ(2026-09-01 実装)

**背景**: ドラッグでの移動・ホイールでのサイズ変更は実装済みだったが、ユーザーから「四隅をドラッグでサイズ変更できるようにしたい」との要望。デザインツール（Figma/PowerPoint等）でおなじみの、選択枠の角をつまんで拡大縮小する操作感が欲しいとのこと。

**対応**: ホバー中に表示される既存のハイライト枠（`#adjustHighlight`）に、四隅の小さいハンドル（`.resize-handle`、CSS絶対配置の12px四方）を追加。ハンドルをドラッグすると、そのハンドルが動いた分だけ`scale`（既存の数値入力・ホイールと同じプロパティ）を変化させる。

- リサイズの基準は「要素のバウンディングボックスの中心から、ドラッグ中の角までの距離」。ドラッグ開始時にその距離を記録しておき、ドラッグ中の距離が伸びれば拡大、縮めば縮小という比率で`scale`を決める（`newScale = startScale × (現在距離 / 開始距離)`）。dx/dyには触れず、あくまで数値入力・ホイールと同じ「スケールを変える」操作の別の入力手段という位置づけ——要素ごとに実際の描画アンカー（中央揃え/左揃えなど）が違うため、「つまんだ角の反対側を固定してリサイズ」という厳密な挙動をテンプレート横断で正しく再現するのは大掛かりになりすぎると判断し、既存のスケール概念に統一した。
- ハンドルは`pointer-events:auto`（親の`.adjust-highlight`自体は引き続き`pointer-events:none`）。ドラッグ判定は`state.elementBounds`頼みのヒットテストではなく、ハンドル自体が実DOM要素としてマウスイベントを受け取る素直な仕組み。
- 実装中に見つけた副作用: キャンバス上でホバー中の要素の枠が見えている状態からハンドルへマウスを動かすと、ハンドルは`canvas`要素の上に重なる兄弟要素のため、ブラウザは「`canvas`からマウスが離れた」と判定して`mouseleave`を発火する。これに反応してハイライトを隠す実装のままだと、ハンドルにマウスを乗せた瞬間に枠自体が消えてしまい掴めない、という不具合が起きるところだった。`mouseleave`の監視対象を`canvas`単体から親の`#canvasWrap`（キャンバスとハイライト枠の両方を含む）に変更し、キャンバス⇄ハンドル間の移動では発火しないようにして回避した。
- ドラッグ中の状態管理（`resizeState`）・Undo/Redoへの統合（`recordAdjustmentChange()`/`commitAdjustmentUndoGroup()`）・画面外までドラッグを追従させる`window`バインドのmousemoveは、既存の移動ドラッグ（`dragState`）とまったく同じパターンを踏襲。

**動作確認**: SE角（右下）を中心から遠ざける方向にドラッグしてscaleが100→243に増えることを確認。Undoで100に復元後、NW角（左上）を中心から遠ざける方向で186に増加、中心に近づける方向で118まで減少と、4隅とも方向が正しく効くことを確認。ドラッグ中に`canvas`の`mouseleave`だけを発火させてもハイライトが消えないこと（`#canvasWrap`を離れた場合のみ消えること）を確認。既存の移動ドラッグ・ホイールリサイズ・6テンプレート全ての通常レンダリングに影響が無いことも確認済み。

## タイトルフォントの選択(2026-09-01 実装)

**背景**: これまで展示会タイトル（および⑤サイバーUI型のキャッチコピー）のフォントは`TITLE_FONT_STACK`定数で固定（Oswald＋Noto Sans JP）だった。ユーザーから「フォントを変更したい場合はどうするか」という相談があり、案としてカスタムフォントファイルのアップロードより先に、あらかじめ用意した数種類から選ぶドロップダウン方式を提案・合意。作品の世界観に応じて数クリックで印象を変えられるようにした。

**対応**: `TITLE_FONT_PRESETS`（key→{label, stack}）を5種類定義し、「テキスト項目」フィールドセットに「タイトルフォント」ドロップダウンを追加。選択は`state.titleFont`（プロジェクト単位、テンプレート/配色と同様に全言語・一括生成で共通）に保存され、`render()`の先頭で`TITLE_FONT_STACK`（`const`→`let`に変更）をそのプリセットの値に差し替える。各テンプレート内の描画コードは元々ローカル変数`TITLE_FONT_STACK`を参照しているだけなので、32箇所以上ある呼び出し側は一切変更不要だった。

- プリセットは5種類: 太字ゴシック（デフォルト、Oswald＋Noto Sans JP）／明朝・上品（Playfair Display＋Shippori Mincho）／丸ゴシック・ポップ（Fredoka＋M PLUS Rounded 1c）／サイバー・近未来（Orbitron＋Noto Sans JP）／シンプル・ゴシック（Inter＋Noto Sans JP）。いずれも「デザイン性のあるLatin書体を先頭、CJKグリフをカバーする同系統の書体を2番目」という既存のOswald+Noto Sans JPと同じ並び順（ブラウザのフォント代替がグリフ単位で先頭から探すため、日本語部分だけ自動的に2番目のフォントで描画される）。
- Google Fontsは`<head>`の`<link>`タグ1本にfamilyパラメータを追加する形でまとめて読み込むようにした（プリコネクト設定は既存のものをそのまま利用）。
- **実装中に発見・修正した不具合**: `<link>`タグでフォントを読み込み可能にしただけでは、実際にそのフォントがブラウザにダウンロードされるとは限らない——`<canvas>`への`fillText()`は（実DOM上のテキストと違って）フォント読み込みを自発的にトリガーしない仕様のため、一度もDOM上で使われていないフォントは`ctx.font`に指定してもダウンロードされないまま代替フォントで静かに描画されてしまう。`document.fonts.check()`で確認したところ、既存のOswald/Noto Sans JP（読み込みから今まで実際に使われ続けていたので既にダウンロード済み）はtrueだったが、新規追加した6書体は全てfalseだった。対応として、ページ読み込み時に全プリセットの全書体に対して明示的に`document.fonts.load()`を発行し、完了ごとに`render()`し直すようにした。この過程で二段階の不具合があった: 最初のバージョンはプリセットの先頭フォント（Latin側）だけをロードしており、5プリセット中3つ（先頭以外の2番目＝CJK側が偶然すでに読み込み済みのNoto Sans JPと共通していたもの）はたまたま問題なく動いていたが、Shippori MinchoとM PLUS Rounded 1c（2番目のCJK側が他プリセットと共有されていない2つ）だけが未読み込みのまま残っていた。全8書体を直接列挙してロードする形に直して解消した。

**動作確認**: `document.fonts.check()`で8書体すべてが読み込み済み（true）になることを確認。実際に5プリセット全てで同じ英語タイトル文字列をレンダリングし、書体が明確に異なって描画されることを画像で確認（Oswaldの太い縦長ゴシック、Playfair Displayの優雅なセリフ、Fredokaの丸みを帯びたポップ体、Orbitronの近未来的な幾何学体、Interのシンプルなゴシック体）。非デフォルトのフォント選択状態で6テンプレート全てが正常にレンダリングされることも確認済み。

## タイトルの視認性向上(2026-09-01 実装)

**背景**: ユーザーから「タイトルをもっと目立つようにしたい。他のコピーと似たような感じで出すよりも」との指摘。実データで検証したところ原因が判明した——情報帯型（デフォルト）で実際によくある長さのタイトル（例:「GINTAMA ART EXHIBITION by GAAAT」32文字）は、既存の自動縮小ロジックにより約49pxまで縮んでいた一方、帯のメインコピーは42px（太さ800）。サイズ差がほぼ無く、装飾も無いプレーンな塗りのみだったため「他のコピーと似た感じ」に見えていた。他5テンプレートも程度差はあるが同様の傾向があり、①切り抜き型は32文字級のタイトルが省略記号で切られるケースすらあった。
