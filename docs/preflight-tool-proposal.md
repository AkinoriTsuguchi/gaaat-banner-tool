# GAAAT 入稿チェックツール 実装提案

既存の `入稿チェック_v2.jsx`(Illustrator用ExtendScript)を土台に、
Googleドライブの入稿フォルダ検出・金額の自動照合・Slack通知までを繋ぐための提案。
バナー／リーフレット／ポスターの3ツールと同じ作法(同一オリジンの静的ページ ＋
`shared/` の共通モジュール ＋ ブラウザ内のGoogleログイン)で組む前提で書いている。

## 1. 結論(先に3つ)

1. **1本のプログラムにはできない。2階建てにする。**
   ExtendScriptはIllustratorの中身を読めるがHTTPSを話せない(=シートもSlackも触れない)。
   ブラウザはシートもSlackも触れるがAIファイルの中身を読めない。
   境界を **「JSXはIllustratorの事実だけをJSONに吐く / ブラウザがシートと突き合わせて判定する」**
   に置く。両者を繋ぐのは1個のJSONファイルだけ。

2. **既存JSXのロジックは全部活かせる。ただし6箇所直さないと運用に乗らない。**
   一番効くのは「サイズをアクティブなアートボードしか見ていない」「金額の正規表現が
   `¥12,000` を拾えない」の2つ。どちらも**見逃す方向**のバグなので、今の運用で
   「OKが出たのに不備だった」が起きうる。詳細は 4章。

3. **MVPは「人が触るのは2回だけ」に絞る。**
   フォルダを選ぶ(JSX) → 出てきたJSONをブラウザにドロップ、の2アクション。
   Drive APIでのフォルダ自動検出とSlack自動投稿はPhase 2に回す。
   通知の書式が固まる前に自動投稿にすると、チャンネルが試し投稿で荒れるため。

## 2. なぜ2階建てになるか(制約の整理)

| やりたいこと | Illustrator(JSX) | ブラウザ(既存ツール) |
|---|---|---|
| 画像リンク・生テキスト・アートボード寸法を読む | ○ | × |
| Googleスプレッドシートを読む | **×**(HTTPSを話せない) | ○(既存 `shared/google.js`) |
| Slackに投げる | **×** | △(後述・リレー経由) |
| フォルダ内のファイル一覧 | ○(ローカルマウント時のみ) | ○(Drive API) |

ExtendScriptには `Socket` があるがTLSが無いので、Google APIもSlackも実質叩けない。
逆にブラウザからはAIファイルの構造(リンク画像・テキストフレーム)を読む手段が無い。
だから境界は**この位置にしか引けない**。ここが決まると残りは素直に決まる。

## 3. 全体アーキテクチャ

```
  ① ブラウザ（check/index.html・既存ツールと同一オリジン）
     案件シートを読む ──> 期待サイズ・許容金額の集合をつくる
                          └─> check-config.json をダウンロード
                                        │
                                        │ 入稿フォルダに置く
                                        ▼
  ② Illustrator（check/preflight.jsx）
     フォルダを選ぶ ──> [ol前]/[ol後] のペアを総当りで開く
                       ├─ 画像リンク／サイズ／トンボ／アウトライン判定
                       ├─ [ol前] の全テキストと金額らしき文字列を抽出
                       └─> _入稿チェック結果.json を同フォルダに書き出す
                                        │
                                        │ ドラッグ&ドロップ
                                        ▼
  ③ ブラウザ（同じページ）
     JSONを読む ──> 金額をシートの価格集合と突き合わせ
                  ──> 総合 OK / NG を表示
                  ──> Slack投稿用テキストをコピー（Phase 2で自動投稿）
```

**なぜ既存リポジトリの新規ページ(`check/`)なのか**: `shared/google.js` のOAuth
クライアントIDと、`shared/master-sheet.js` の案件マスタ・パーサをそのまま使えるため。
別オリジンに置くとGoogle Cloud側の「承認済みJavaScript生成元」を足す作業が増える
(`poster/` `leaflet/` を同居させたのと同じ理由)。

## 4. 既存JSXのレビュー

### そのまま活かすもの

- ファイル名の `[ol前]` / `[ol後]` でモードを切り替える設計 — 運用が既にできているので強い
- `doc.placedItems.length` でリンク画像を数える
- `doc.textFrames.length` で生きたテキストを数える
- `artboardRect` を mm に換算して期待値と照合する
- レイヤー名(`トンボ` / `crop` / `trim`)でのトンボ簡易判定
- 金額らしき文字列にフラグを立てて人に見せる

### 直したいところ(重要度順)

1. **サイズがアクティブなアートボード1枚しか見ていない**
   (`入稿チェック_v2.jsx:52` `doc.artboards.getActiveArtboardIndex()`)
   リーフレットは表面／裏面で2アートボードのことがあり、**片面が未検査のまま通る**。
   全アートボードをループして、期待サイズの集合と突き合わせる。

2. **金額の正規表現が一番よくある表記を拾えない**
   (`入稿チェック_v2.jsx:103` `/[0-9][0-9,，]*\s*(円|¥|￥)/`)
   数字が**先に**来る形しか見ないので、`¥12,000` のように記号が先頭に来る表記が
   素通りする。全角数字(`１２，０００円`)も拾えない。
   `/(?:[¥￥\\]\s*[0-9０-９][0-9０-９,，]*)|(?:[0-9０-９][0-9０-９,，]*\s*円)/g` に置き換える。

3. **期待サイズがスクリプト冒頭のハードコード**(`EXPECTED_WIDTH_MM` / `EXPECTED_HEIGHT_MM`)
   案件ごとに人が書き換える運用は必ず事故る(前の案件の値のままチェックが通る)。
   同じフォルダの `check-config.json` から読み、無ければ現状の既定値で動きつつ
   「期待値がシート由来ではない」と結果に明記する。

4. **トンボ判定がトップレベルのレイヤー名しか見ていない**
   `doc.layers` はサブレイヤーを含まない。トンボをサブレイヤーに入れている場合や、
   レイヤーを分けずオブジェクトで置いている場合は**毎回「要確認」**が出て、警告が形骸化する。
   - サブレイヤーを再帰で探す
   - あわせて幾何でも見る: アートボード外に3mm以上はみ出したオブジェクトがあるか
     (＝塗り足しの実在)。名前ベースより実態に近い。

5. **`alert()` は行数が増えると打ち切られてスクロールできない**
   リーフレットは作品ごとに価格が入るのでテキストが数十〜百件になり、
   `listTextContents()` の一覧が実質読めない。結果はJSONファイルに書き出す。

6. **`doc.textFrames` はシンボル定義内・配置EPS内のテキストを見ない**
   0件でも「絶対に生テキスト無し」とは言い切れない。結果に但し書きを出して過信を防ぐ。
   同様に、リンク画像の判定は `placedItems` に加えて `rasterItems[i].embedded === false`
   も見ておく(バージョンによってリンクラスターがこちらに来る)。

### 安いわりに効く追加(5種の不備の外側だが1行〜数行)

- **`[ol前]` の更新日時が `[ol後]` より新しい場合に警告** — アウトライン後に
  `[ol前]` を直して `[ol後]` を作り直し忘れた、という事故を検出できる。ファイルを開かずに判定可。
- **`doc.documentColorSpace` がRGBなら警告** — 入稿不備の定番。
- **埋め込み画像の実効解像度**(ラスターの元px ÷ 配置サイズ)が低い場合の警告 — 任意。

## 5. 金額チェックの設計

### 正(ただしい金額)はどこにあるか

既存のリーフレットツールは**EC作品シート**から価格を取っている
(`leaflet/app.js:147-149` の `価格(税込)` / `価格(税抜)` / `価格(ドル)`)。
一方 `shared/master-sheet.js` が読む案件マスタには企画タイトル・コピーライト・
会期・会場しか無く、**金額欄が無い**。
したがって金額の正はEC作品シート側だと考えている(→ 8章 Q3で確認したい)。

### 照合の向きは「一致」ではなく「包含」

リーフレットには作品ごとの価格が何十件も載るので、1対1の一致比較は成立しない。

- **AIから拾った金額の集合 ⊆ シートの価格の集合** ならOK
- シートに無い金額が1つでもあればNG(＝誤記か、シートが未更新)
- 逆に**シートにあってAIに無い**のはNGにしない(その作品を載せていないだけ)。情報として出す

これで「作品点数×価格の全件を人が目視する」という現行の一番重いコストが消える。
人が見るのは「金額らしいが許容集合に無かったもの」だけになる。

### 正規化

`¥12,000` `12,000円` `12000` `￥12,000-` `12,000円（税込）` `１２，０００円` を
すべて `12000` に落としてから比較する。
AI側の文字列からは税込／税抜／ドルのどれかを判別できないので、
**税込・税抜・ドルの全部を許容集合に入れる**(厳密さより誤検知の少なさを取る)。

## 6. Slack通知の設計

**ブラウザから Incoming Webhook を直接叩くのはやめたい。**
Webhook URLは実質シークレットで、静的サイトのJSに書くとページを開ける人全員が
そのチャンネルに任意の投稿をできてしまう。CORSの都合でレスポンスも読めず、
投稿の成否が分からない。

代わりに **既存のApps Scriptに `doPost` を1本足してリレーにする**のが一番安い。
WebhookURLはスクリプトプロパティに置けば表に出ない。Slack連携は既に動いているので、
新しく作るのは中継の数十行だけ。

ただし**MVPでは自動投稿しない**。「Slack投稿用テキストをコピー」だけにして、
貼るのは人。書式が固まってから自動化する。

## 7. MVPと進め方

### Phase 1 — これだけで運用に乗る

- `check/preflight.jsx`
  フォルダを選ぶ → `[ol前]`/`[ol後]` のペアを総当りで開く → 4章の修正を入れたチェックを実行
  → `_入稿チェック結果.json` を同フォルダに書き出す → 開いたファイルは保存せず閉じる
- `check/index.html` + `check/app.js`
  既存の `shared/google.js` `shared/master-sheet.js` をそのまま使う同一オリジンの新規ページ。
  案件シートを読む → `check-config.json` をダウンロード → JSXの出したJSONをドロップ →
  金額照合 → 総合OK/NG表示 → Slack用テキストをコピー

人が触るのは「フォルダを選ぶ」「JSONをドロップ」の2回。

### Phase 2 — 自動化を進める

- Drive API(既存の `drive.readonly` スコープで足りる)でフォルダ内のファイル一覧を読み、
  ペアの有無と更新日時の前後を**Illustratorを開く前に**ブラウザ側だけで判定
- 結果JSONのDrive書き戻し(`drive.file` スコープの追加が必要)
- Apps ScriptリレーでSlack自動投稿
- 制作物管理マスタに「入稿チェック済み」を書き戻す

### Phase 3 — Illustratorを外せる可能性

入稿がPDFなら、**pdf.js でブラウザだけで**次を読める:
MediaBox/TrimBox(=サイズ・塗り足し・トンボの有無)、テキストオブジェクトの有無
(=アウトライン判定)、埋め込みフォントの一覧、画像の解像度。
AIとPDFの両方を入稿しているなら、**こちらが本命になりうる**
(Illustratorを開かずに済む＝チェックをクラウド側に寄せられる)。
→ 8章 Q1の答え次第で、Phase 3を前倒しする判断もある。

## 8. 確認したいこと

**Q1. 実際の入稿形式はAIとPDFのどちらか。**両方ある場合、どちらが「入稿した現物」か。
PDFが現物なら、Phase 3(ブラウザだけで完結)を先にやったほうが安く強い可能性がある。

**Q2. Googleドライブは「パソコン用Google ドライブ」でローカルにマウントしているか。**
この開発機を見た限り、マウントされているのは OneDrive(株式会社GAAAT)だけで、
Googleドライブのマウントは無い。JSXがフォルダを直接読むにはマウントが要る。
無い場合の代替は「ブラウザからフォルダごとダウンロード → ローカルで実行」になり、
手数が1つ増える。

**Q3. 金額の正はEC作品シートの `価格(税込)` 列でよいか。**
それとも制作物管理マスタ側に金額欄があるか。リーフレットに載る価格は作品ごとに
複数あるはずなので、5章の「包含」判定でよいかもあわせて確認したい。

**Q4. 期待サイズの正はどこか。**制作物管理マスタに制作物ごとのサイズ列(A4三つ折り／
A1／210×297 等)はあるか。無ければ `check/` のページで手入力＋案件名に紐づけて保存する形にする。

**Q5. トンボの運用ルール。**レイヤー名を「トンボ」で統一しているか。塗り足しは3mmで固定か。
実データを1案件ぶん見せてもらえると、名前ベースをやめて幾何判定に寄せられる。

**Q6. Slackの通知先チャンネルと書式。**OK時も投げるか、NG時だけか。
デザイナーへのメンションは要るか。既存のApps ScriptのWebhookを流用してよいか。

**Q7. 誰がこのチェックを実行するか。**デザイナーが納品前に自分で回すのか、
マーケ担当が受け取り時に回すのか。前者なら「NGなら止まる」寄り、
後者なら「NGでも記録してSlackに流す」寄りに、既定の挙動が変わる。

**Q8. 実データを1案件ぶん(`[ol前]`/`[ol後]` のAIと、対応するシート)いただけると、
Phase 1を作りながら実物で検証できる。** 特にトンボとサイズは、実際の作りを見ないと
判定のしきい値を決められない。

## 9. 実データで確認したこと(2026-09-04)

共有いただいた入稿フォルダ(`R228_機動警察パトレイバー_リーフレット`)と
EC サイトのシートを実際に見て分かったこと。**設計判断が2つ変わる。**

### フォルダの中身

直下:

| ファイル | 更新日時 | サイズ |
|---|---|---|
| `[ol前]R228_機動警察パトレイバー_リーフレット.ai` | 08-18 06:27 | **425 MB** |
| `R228_機動警察パトレイバー_リーフレット.pdf` | 08-18 06:31 | **424 MB** |
| `[ol後]R228_機動警察パトレイバー_リーフレット.ai` | 08-18 06:33 | **425 MB** |
| `old/` (サブフォルダ) | | |

`old/` の中には **まったく同じファイル名のまま4世代分**、計12ファイルが入っている。
8/10 世代は1ファイル **3.26 GB**。`old/` だけで約 17.3 GB、フォルダ合計で **約 18.5 GB**。

### 変更点1: ブラウザにダウンロードしてチェックする案は捨てる

1案件の現行3ファイルだけで 1.2 GB。旧世代を含めれば桁がひとつ増える。
ブラウザで落として `pdf.js` に食わせる Phase 3 は、**この規模では成立しない**
(424 MB の PDF をブラウザのメモリに載せられない)。
入稿形式がAIであるという回答ともあわせて、**Phase 3 は取り下げる。**

残る現実的な形は、**ローカルにあるファイルをその場でIllustratorに開かせる**一択。
そのためにドライブがFinderの中にフォルダとして見えている必要がある(→ 下の補足)。

### 変更点2: ペア検出は「直下のみ・更新日時でタイブレーク」

`old/` に同名ファイルが4世代あるので、フォルダを再帰的に探すと
**どれが現物か決められなくなる**。したがって:

- サブフォルダには降りない(`old/` `旧` `bak` 等は明示的に無視)
- 同名が複数見つかった場合は更新日時が最新のものを採用し、**その旨を結果に出す**

### 提案した「更新日時チェック」は実データで発火する

`old/` の 8/10 10時台の世代は、

- `[ol後]` 10:23:38
- `[ol前]` 10:27:34 ← **[ol後]より新しい**

つまり**アウトライン化したあとに `[ol前]` を直して、`[ol後]` を作り直していない**。
4章で「安いわりに効く追加」として挙げたチェックが、実物で1件目から当たっている。
ファイルを1バイトも開かずに判定できるので、**Phase 1の最初に入れる**。

なお現行世代は `[ol前]` 06:27 → PDF 06:31 → `[ol後]` 06:33 の順で、こちらは正常。

### Illustratorを開くコスト

425 MB のAIを2本開くので、1案件あたり数分かかる前提で組む。JSXは
「開く → 調べる → **保存せず閉じる**(`doc.close(SaveOptions.DONOTSAVECHANGES)`)」を
1ファイルずつ確実にやる。まとめて開くとメモリを踏み抜く。
進捗はScriptUIのプログレスバーで出す(無反応に見えて強制終了されるのを防ぐ)。

### 金額の正: EC サイトのシート

`GAAAT-Gallery  ECサイト`(57 MB / 最終更新 2026-09-04)。
「基本的に全案件このシートにまとまっている」との回答なので、5章の設計どおり
**このシートの価格列を正とし、「包含」で照合する**方針で確定してよいと考えている。

ただしシートが 57 MB あるため、**タブ(gid)を指定して必要な範囲だけ読む**。
全体を読むと重すぎる。既存の `leaflet/app.js` が同じシートを
`#gid=` 付きURLで読んでいるので、その読み口をそのまま使う。

### 補足: 「マウント」とは(Q2の言い換え)

「**パソコン用 Google ドライブ**」というGoogleの無料アプリをMacに入れると、
Googleドライブの中身が **Finderの中に普通のフォルダとして出てくる**。
実体はクラウドにあって、開いたときだけ中身が降りてくる(全部を先にダウンロードはしない)。
この状態を「マウントされている」と呼んでいる。

これが要るのは、**Illustratorのスクリプトは「Finderで開けるフォルダ」しか扱えない**ため。
入っていれば「入稿フォルダを選ぶ → 中の `[ol前]`/`[ol後]` を自動で見つけて全部チェック」
が成立する。入っていないと、毎回 1.2 GB を手でダウンロードすることになり運用に乗らない。

この開発機には入っていなかった(`~/Library/CloudStorage/` にあるのは OneDrive のみ)。
チェックを回す人のMacに入れてもらうのが、Phase 1 の唯一の前提条件になる。

## 10. 確定した方針（2026-09-04）

回答をもらって決まったこと。実装は [preflight-tool.md](preflight-tool.md) に移した。

| 論点 | 決定 |
|---|---|
| 入稿形式 | **.ai が現物**（PDFは補助）。Phase 3（pdf.js）は取り下げ |
| 金額の正 | **ECサイトのシート**。見出しに「価格」を含む列から許容集合を作り、包含で照合 |
| トンボ | レイヤー名の運用は不明 → **名前ベースを主判定にしない**。塗り足しの実測値(mm)で見る。塗り足しは **3mm 固定** |
| Slack通知 | **作らない**。「ツール上で確認できればOK」。画面に「結果をテキストでコピー」だけ置く |
| 実行者 | **マーケ側が受け取り時**に回す。NGでも止めず、内容を見せる作りにする |

### 実装時に変えた設計（提案書からの差分）

**`check-config.json` を廃止した。**
提案書では「ブラウザが期待値をJSONで書き出し → JSXが読む」という3ステップにしていたが、
**JSXは期待値を知らなくてよい**ことに気づいたのでやめた。
JSXは「アートボードは 297×210 mm だった」と事実を出すだけにして、
それが正しいかはブラウザが判断する。

これで人の操作が3回から2回（フォルダを選ぶ / JSONをドロップ）に減り、
「JSXに案件ごとの数値を持たせない」という当初の狙いもより素直に満たせる。

同じ理屈で、**金額の抽出もブラウザ側でやり直す**ことにした。JSXが運ぶのは生テキストだけ。
抽出ルールを直したいときに、各人のMacに配ったJSXを配り直さずに済む。

### 残っている確認事項

- **トンボの実データ**: `[ol前]`/`[ol後]` を1案件ぶん実際にチェックにかけて、
  塗り足しの実測値がどう出るかを見たい。アートボードが「仕上がり」と
  「トンボ込み」のどちらで作られているかで、初期値の出し方が変わる
- **ECサイトのシートのタブ**: どのタブに価格が入っているか。
  いまは開いているタブ（`#gid=`）を読む作りにしてある
- **仕上がりサイズの既定**: いまは画面のプルダウン（A4三つ折り 297×210 を既定）。
  制作物管理マスタにサイズ列があるなら、そこから引いたほうが事故が減る
